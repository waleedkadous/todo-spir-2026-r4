## KEY ISSUES

### 🔴 Medium — `searchText` is a dead field (spec mismatch)

`NLFilterAction` in `types/todo.ts:58` defines `searchText?: string`, and the spec mentions `searchText` in the filter action schema. However:
- The system prompt in `gemini.ts` does **not** mention `searchText` to the model
- `nl-executor.ts` `executeFilter()` ignores it entirely
- No UI component consumes it
- The spec also mentions `dateRange` as a filter payload field — also absent from the implementation

This is harmless dead code, but it's a spec divergence. Either implement `searchText`/`dateRange` support or remove the field from the type to avoid confusion. Given the plan doesn't mention these features either, removal is the cleaner option.

### 🟡 Low-Medium — `parseGeminiResponse` validates action type but not payload shape

The parser at `gemini.ts:110-135` checks that `action` is one of the five known types, then casts to `NLAction` with `as`. It does **not** validate that:
- An `add` action actually has a `title` field
- An `update` action has `todoIds` and `updates`
- A `delete` action has `todoIds`
- An `error` action has `message`

The executor does have some guards (e.g., checking `!action.title`, `!action.todoIds`), which partially compensates. But a malformed Gemini response like `{"action": "update"}` would pass the parser and reach the executor where it hits the `todoIds.length === 0` check and returns a confusing "No todos specified for update" message rather than a clear "malformed AI response" error. The spec calls for "strict validation of response shape" (plan line 255). Consider adding payload validation in the parser.

### 🟡 Low-Medium — NL input sends entire todo list to API on every request

`NLInput.tsx:56-60` sends the full `todos` array in the POST body. For a single-user localStorage app this is fine at small scale, but the spec acknowledges "hundreds of todos max." With hundreds of todos, each containing title + description + all fields, the request body could grow to 100KB+, and the system prompt will bloat accordingly. The Gemini context window handles this, but it adds latency and token cost.

Not blocking, but worth noting. A future optimization could truncate descriptions or limit the number of todos sent.

### 🟡 Low — Toast `onDismiss` stability may cause re-renders

`Toast.tsx:13` uses `onDismiss` in the `useEffect` dependency array. In `page.tsx:93`, `onDismiss` is an inline arrow `() => setToast(null)` — a new reference every render. This means the Toast's `useEffect` will re-run on every parent render, resetting the 4-second timer. In practice this is unlikely to cause visible bugs (the parent doesn't re-render frequently while a toast is showing), but it's technically incorrect. Wrapping the dismiss handler in `useCallback` or stabilizing it would be more correct.

### 🟢 Low — No integration test for the API route

The test plan calls for "Integration Tests: Full NL flow: input → API route → parse → execute → state update (with mocked Gemini)." The existing tests cover the parser and executor in isolation, but there's no test for `api/chat/route.ts` itself — e.g., that it returns 503 when unconfigured, 400 on bad input, or correctly passes through to `callGemini`. This is a gap vs. the plan's test requirements.

### 🟢 Low — Minor: dismiss button uses plain "x" not "×"

`Toast.tsx:32` renders `x` (lowercase letter x) instead of `×` (`&times;`) or an SVG icon for the dismiss button. Cosmetic only.

## What's Done Well

- **System prompt engineering** is solid: low temperature (0.1), clear schema definitions, current todo context, date context for relative dates, ambiguity instructions
- **Error handling cascade** is comprehensive: 503 → unavailable, 504 → timeout, 400 → bad request, 500 → generic, with user-friendly messages at each level
- **Filter wiring** is elegant: NL filter actions call the same `setFilters` that the FilterBar uses, so state stays in sync
- **Timeout handling** with `AbortController` + 10s limit matches spec exactly
- **Debounce** via timestamp ref (not `setTimeout`) prevents double-submits without delaying the first submit
- **Type system** is well-designed: discriminated union on `NLAction` enables exhaustive switch handling in the executor
- **Graceful degradation**: app works fully without `GEMINI_API_KEY` — NL just shows unavailable message
